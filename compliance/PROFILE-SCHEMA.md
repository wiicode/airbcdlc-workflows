# Framework profile — the question set every framework note must answer

Write the note as Markdown with these numbered sections, in this order. Cite the source text by page (`p.NN`) or clause/requirement id for every factual claim. Where you rely on general knowledge because the source on hand does not cover it, mark the sentence `[general knowledge — verify]`. Quote key sentences verbatim (short). Be concrete; no filler.

1. **What kind of thing it is.** Attestation / certification / contractual standard / regulation / voluntary framework / guidance. Who issues it, who assesses against it, who enforces, who can "fail" you and on what authority. Exact vocabulary the framework uses for itself (e.g., "attestation", "certification", "compliance", "report on compliance", "conformity").
2. **Who it applies to and what triggers scope.** The scoping rules in the framework's own terms (e.g., cardholder data environment; ISMS scope statement; system boundary; organizational profile). What is explicitly OUT of scope or excludable, and how exclusions must be justified.
3. **How the document is structured.** Mandatory parts vs. reference/guidance parts; requirements vs. test procedures vs. guidance; numbering scheme; themes/domains/functions; counts (how many requirements/controls/criteria). What is normative and what is informative.
4. **What it actually requires — and what it does NOT.** The real obligations in plain language; the most common misreadings ("you must have X") that the text does not support; where the framework explicitly leaves design to the organization.
5. **How risk appears in it.** Every place risk assessment, risk treatment, risk acceptance, targeted risk analysis, risk owner, or appetite/criteria appears; what the framework requires to be documented about risk decisions; whether accepting a risk is a permitted outcome and how it must be recorded.
6. **Flexibility points.** Customized approaches, compensating controls, Statement of Applicability exclusions, management-defined criteria, tiers/profiles, "defined approach vs customized approach" — anything that lets an organization substitute its own control for the framework's wording, and the evidence the framework demands for doing so.
7. **Assessment and evidence mechanics.** Type 1/Type 2 periods; Stage 1/Stage 2, surveillance, recertification; ROC/SAQ/AOC, assessor types (QSA/ISA), merchant/provider levels; self-assessment; what evidence looks like; sampling; what "operating effectiveness" or "in place" means; report consumers.
8. **Vocabulary that must be used precisely.** Terms the framework defines that a program must not blur: control vs control objective vs criterion vs requirement vs point of focus; finding vs vulnerability vs weakness; in place / not in place / not applicable / not tested; residual vs inherent; etc. Quote definitions.
9. **Where a 50–500-person company's pragmatism applies.** What such a company should actually do first; what is a trap (over-scoping, over-documenting, buying tooling before deciding); what the framework itself says about proportionality or small entities.
10. **Hooks for AI-RBCDLC.** Which program objects satisfy which parts: obligations, tolerances, risks/decisions, controls (library + implementation), policies, evidence, tasks, inventory (people/devices/systems/vendors/data stores). Which framework artifacts can be COMPILED from the program as views (e.g., Statement of Applicability; PCI scope statement and network/data-flow description; SOC 2 system description and control matrix; CSF Organizational Profile; risk treatment plan). Which parts need the organization's own licensed copy of the text (copyright) vs. what identifiers/titles the module could carry.
11. **Key quotes with page refs.** 10–20 verbatim sentences the compliance module should be able to cite when answering questions.
12. **Open questions / gaps in the source on hand.**
